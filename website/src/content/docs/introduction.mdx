Toka is a no-GC systems programming language designed around explicit resource semantics. It keeps zero-cost performance and static safety as baselines, makes real systems semantics visible, and tries to keep everyday systems code readable, writable, and maintainable.

## Design Position

Toka does not treat performance, safety, and simplicity as three independent slogans. Performance and static safety are the floor. The design question is what kind of syntax and compiler discipline can keep that floor while reducing accidental complexity in everyday systems code.

That does not mean minimizing syntax at all costs. Toka aims for the minimum surface needed to expose real systems semantics: a piece of notation should earn its place by making ownership, access, representation, failure, or control-flow boundaries easier to see and audit.

That leads to a few recurring principles:

- source code should show the operation that actually matters;
- mutation, rebinding, transfer, and nullability should not be visually ambiguous;
- resource ownership should be explicit enough for static checking;
- low-level representation should be available without making raw pointer style the default API shape.

## Core Model

Toka separates two layers that many systems languages collapse into one notation:

| Layer | Meaning | Examples |
| :--- | :--- | :--- |
| Payload / Soul | The object content being read, written, passed, or matched | `x`, `x.field`, `x = value` |
| Handle / Representation | The way an object is reached, owned, borrowed, shared, or rebound | `&x`, `*x`, `^x`, `~x`, `*x = *y` |

Plain names operate on payload. Hats operate on handle identity. That is why `p = value` and `*p = *q` are different operations: one writes object content, the other rebinds a raw handle.

## Resource Contracts

Toka uses compact markers for distinct resource facts:

| Marker | Role |
| :--- | :--- |
| `#` | Payload mutability, or handle rebinding authority when placed after a hat |
| `?` | Nullable payload type state |
| `nul` | Nullable handle marker |
| `&` | Borrow/reference handle |
| `*` | Raw pointer handle |
| `^` | Unique owning handle |
| `~` | Shared owning handle |
| `cede` | Explicit resource-transfer contract |

For ordinary object parameters, Toka uses logical in-place capture. A function writes `x: T` or `x#: T` when it wants the payload view. It puts a hat on a parameter only when it needs the handle itself, for example to forward or rebind that handle.

`cede` is both permission and obligation. If a function signature requests `cede`, the body must explicitly consume, forward, store, return, or otherwise complete that transfer path.

## Language Surface

The current implementation includes named `shape` construction, enum-like variants, traits and `impl` blocks, morphic generics, deterministic cleanup, `Result` / `Option` failure propagation with postfix `!`, `async` / `.await`, pattern matching, and native compilation through LLVM 20.

The language and ecosystem are still young. The near-term engineering focus is compiler hardening, standard-library stabilization, Windows parity, incremental build reliability, and eventual self-hosting.

## A Quick Taste

```toka
import std/io::println

shape Resource(val: i32)

fn keep(cede r: Resource) -> Resource {
    return cede r
}

shape Rect (
    width: i32,
    height: i32
)

impl Rect {
    pub fn area(self) -> i32 {
        return self.width * self.height
    }
}

fn main() -> i32 {
    auto r = Rect(width = 10, height = 20)
    println("Area: {}", r.area())

    auto owned = Resource(val = 42)
    auto moved = keep(cede owned)

    if moved.val != 42 {
        return 1
    }
    return 0
}
```
