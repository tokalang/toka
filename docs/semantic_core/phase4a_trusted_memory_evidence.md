# Phase 4A Trusted Cross-Module Memory Evidence

Phase 4A freezes the trust model for carrying body-derived memory evidence
through Toka's compiler-owned build cache. It introduces no source-language
syntax and does not make ordinary `.tki` metadata a trust credential.

## Purpose

Phase 3 established verified source-body summaries and a gated backend
consumer. Same-module LLVM optimization can infer most of the same facts, but
a source-less declaration is deliberately reduced to `SignatureOnly`. The
remaining useful case is a separately compiled provider whose interface and
backing object were produced together by the current compiler.

The cache evidence exists only to describe that fixed backing object to later
compiler invocations. It is not a promise supplied by source code, a package,
or an interface author.

## Trust Boundary

A memory-evidence artifact is trusted only when all of these hold:

- the resolver selected a compiler build-cache `.tki`, not an arbitrary
  source-less interface;
- the cache entry has a backing object selected for linkage;
- compiler version, evidence schema, interface format, target triple, and
  source hash match the selected interface;
- the evidence records the SHA-256 digest of the exact backing object and the
  current object has that digest; and
- every record is structurally valid and maps to a declaration in the
  selected interface.

The object digest is the body binding. A cache consumer already trusts the
selected object as executable linker input; the digest prevents a stale or
unrelated summary from being paired with it. This does not grant trust to
standalone `.tki` files, ordinary include paths, package mappings, or metadata
that merely claims to be generated by Toka.

## Artifact Contract

The compiler-owned sidecar uses internal JSON schema
`toka.trusted-memory-evidence` version 1. It contains:

- compiler and interface format versions;
- target triple and source hash;
- backing-object SHA-256;
- deterministically ordered function records; and
- the conservative function/root effects already defined by the Phase 3C
  memory-summary lattice.

The sidecar is stored beside the build-cache interface with the same stem and
the `.tke` extension. It is an internal cache artifact, not a public interface
format or compatibility commitment.

## Use Restrictions

- Cached body evidence never changes parsing, type checking, PAL, ownership,
  effects, async acceptance, diagnostics, or ordinary TKI replay.
- It may only refine `SignatureOnly` memory summaries after semantic checking
  has completed.
- Backend attributes still pass their own contract-specific gate. A trusted
  summary does not bypass ABI checks, disabled borrow checking, unsafe/raw
  degradation, async restrictions, or the separate `noalias` gate.
- `--disable-borrow-check` cannot consume PAL-dependent cached facts.
- Generic instances not represented by a concrete cached symbol remain
  conservative.

## Failure Policy

Missing, malformed, stale, mismatched, tampered, or unsupported evidence is a
cache miss, not a language error. The importer records a stable rejection
reason and retains `SignatureOnly`. Compilation must remain behaviorally
equivalent to using the ordinary source-less interface without evidence.

An artifact that passes identity checks but contains an invalid record is also
discarded in full. Partial trust is forbidden so that record omission or
duplication cannot produce order-dependent results.

## Phase Gates

- Phase 4B implements deterministic export, validation, conservative import,
  and observable cache status.
- Phase 4C proves source/cache/source-less replay and every downgrade path,
  including object and sidecar tampering.
- Phase 4D permits experimental cross-module `nocapture` only from validated
  evidence, then repeats the optimization and benefit audit.

`readonly` and `writeonly` remain shadow-only during Phase 4. `noalias`
remains a separate final soundness task.
