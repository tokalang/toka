# 0.12.x 开发线：项目开发体验

状态：2026-10-02 设计基线；尚未实现、未冻结 0.12 SDK、未启动完整发布资格矩阵。
本批交付仅包含此文、[toka test v1 契约](toka_test_v1.md)和
[验收矩阵](toka_test_v1_acceptance.md)。设计承诺不能记作已通过实现测试。

## 目标与范围

用户与 AI 使用已安装的发布 SDK，独立完成创建项目、管理依赖、检查、测试、
运行和交付，不依赖编译器源码目录、维护者手工补路径或不公开的构建命令。

0.12 的主功能是正式 `toka test` v1：普通测试程序入口、确定的选择行为、同项目
锁定依赖、串行调度、独立产物、可监管进程、有界超时/清理、准确结果与 JSON。
属性测试、覆盖率、测试宏、任意测试函数扫描、复杂测试框架和项目内并行调度
不进入 v1。并发 CLI 调用互不覆盖是 v1 必须满足的基础安全性，不等于并行测试功能。

## 0.12 平台支持政策（独立实现提交）

政策 ID：`toka.release-platforms.0.12.v1`。以下是待部署的 0.12 规则，不是当前
工作流已修改的声明。平台提交必须在 0.12 候选资格运行前完整通过契约测试。

| 目标 | 支持等级 | 是否阻断核心发布 | 二进制提供条件 |
| --- | --- | --- | --- |
| Linux x64 | 正式 | 是 | 同候选完整资格、包重放与摘要通过 |
| Linux ARM64 | 正式 | 是 | 同候选完整资格、包重放与摘要通过 |
| macOS ARM64 | 正式 | 是 | 同候选完整资格、包重放与摘要通过 |
| macOS x64 | 独立尽力支持 | 否 | 同候选实际包的基本运行验证通过后才提供 |
| Windows GNU x64 | 源构建/dogfood | 不纳入发布 SDK 资格集 | 本版没有官方 Windows SDK 包承诺；test 监督能力按 C4 明确报错 |

核心资格只有三个正式目标，并继续对同一个不可变 SHA 执行完整验收。Intel 是
独立非阻断任务，不能挂在必须等待其完成的 summary needs 上而继续拉长核心发布。
该任务可按需执行；为某版本提供 Intel 包时必须先取得该包的基本验证回执。若核心
发布时还没有回执，该次资产集不包含 Intel，状态明确为 not_run 或仍未完成的
running，不标为 pass。结束后明确为 passed/failed；失败也不影响已通过的核心集。

optional 状态允许 `not_run|running|passed|failed`；passed 还必须记录 validation_level
为 basic 或实际完成的 full。0.12 的核心资格 pass 不是“完整四平台 pass”。
Intel 失败/未完成时，不能把未经验证的包挂上去；若未来补发可选包，作为独立的
受审资产变更，更新完整校验和和推广证据，不自动改写已验证资产集。

### 一次同步的政策迁移

平台策略提交独立于测试命令实现，同时修改以下边界及正反用例 V01–V12：

1. 支持说明与 0.12 release 文案：明确三正式平台、Intel 尽力支持和缺包行为。
2. 工作流与资格汇总：版本绑定 policy_id、expected_core_targets 和 optional
   状态；不以宽松文件数量判断资格，不等待非阻断 Intel 作业。
3. 资产检查：核心三包 + SHA256SUMS 是必需集合；可额外包含唯一经验证的 Intel
   包。额外未知包、重复包、缺核心包、Intel 无回执、错 SHA/版本/摘要均拒绝。
4. SDK 重放：三个核心包都取得同候选实际发布字节的重放回执；Intel 的重放不再是
   核心发布前置，但包含 Intel 包时其 basic 回执是资产接纳的前置条件。
5. draft 与推广：只使用冻结原包，绑定 source run **及 attempt**、artifact 身份、
   SHA、版本、policy、包含资产集、各重放回执和所有摘要。不因新增标签重建 SDK。
6. 安装器：正确选择核心目标；Intel 包存在则校验并安装，没有则明确报本版本无
   Intel 二进制，给出源构建指引。不得装 ARM 包、静默降级到旧版本或替用户改平台。

Intel basic 包验证包括：干净解包、工具版本一致、SDK 自定位、项目创建、实际
编译/链接/运行、锁定依赖，以及 test 的小型成功/失败/超时样例。它不替代完整
语言/标准库资格；报告必须注明 basic。参与任一平台工作的 helper 也必须随 SDK
安装，外部宿主依赖列明，不依赖维护者源码树。

版本分派必须明确：`v0.11.N` 沿用原四平台、原资产和 Intel 重放要求；
`v0.12.N` 使用上述政策。不得用新的三平台规则追认历史 0.11 报告。
[0.11.0 发布记录](0_11_development_line.md)、原标签/资格/包/回执保持不变。
政策迁移不得移动版本标签、替换历史资产或修改旧验收结果。

## B0 默认超时数值与反馈基线

待决项只有 **compile_ms/run_ms 的默认数值**；机制、CLI 覆盖、计时边界、固定
2000 ms TERM grace 与 5000 ms kill 后确认上限都已在主契约确定。
此门禁不允许以暂定数字、无限超时或“先实现以后调整”绕过。文档 D0 可以交付，
但 B0 未关闭时不能进入 I1；D0 本身不声称 SDK test v1 已可用。

### 冷热任务与默认值推导

测量协议固定如下，产出的数据随实现评审提交，不占用完整发布矩阵：

- 对照版本为已发布 v0.11.0 的固定 SDK 包和摘要。新候选使用固定 SHA、工具链
  和宿主条件。不能用移动 main 或“最新包”作不可复现对照。
- 微型任务涵盖无依赖、已锁定发布依赖、本地依赖、成功/失败程序；真实项目任务
  涵盖 create/add/check/test/run/既有交付流程。0.11 的 preview test 不支持的行为
  记失败/不支持，不用临时修补 SDK 冒充基线能力。
- 冷路径：新项目副本，没有项目构建产物/语义缓存；依赖缓存为空。依赖获取时间
  单列，同时记录网络和缓存条件。不能宣称清除了无法控制的 OS 页缓存。
- 热路径：同一包/项目和 lock，依赖、编译与语义缓存已准备，重复同一输入；不得
  改源文件冒充同一热任务。记录缓存命中与实际阶段边界。
- 每个核心平台、每项任务各取至少 5 个冷样本和 5 个热样本，记录完整样本、最大
  值、中位数；小样本不伪称精确 p95。Intel 可另测，不决定核心默认数值。
- 按 selection/dependencies/compile_link（或真实 separate）/run/cleanup/report
  和总 wall time 留存。实时输出的开始/结束与原始日志可回看，合并阶段不拆造数据。
- 默认编译/运行预算分别根据相应阶段的核心平台最慢样本及明确记录的波动裕量
  确定。依赖网络时间不塞进 compile 默认值。对明显超过默认值的合法长测，用户
  可显式覆盖；测试程序须在设定预算内设计。记录具体数字与理由并补入契约。
- 不以阈值放宽覆盖失败；另用握手夹具和显式短预算验证 timeout/cleanup 状态机。
  性能目标在真实基线形成后制定，不能用未知用户比例或旧完整 CI 总时长代替。

B0 执行协议现固定为 `toka.b0.sdk-components.v1`，独立测量器位于
`tools/scripts/measure_test_baseline.py`。七项任务固定为 bare_ok、owned_vec_ok、
json_ok、local_dep_ok、registry_dep_ok、compile_reject、run_nonzero；每平台 5 组
cold→hot 配对。冷样本使用原包重新解包与新项目，SDK 自带接口保留；本地依赖的
平台绝对 locator 由 SDK helper 在采样外解析一次，再冻结该对 lock 并清空物化状态。
热样本完整重复既定阶段顺序。direct compile_link 在 check/build 探针前执行；
探针是复合流水线计时，不能当作编译器的独立 compile/link 时长。

锁定发布依赖为 unicode 0.1.1，归档 SHA-256
`c68569e6efbd9eb9bf85226eca68de3a0187d4300e320aeb13857be73b5ad28a`。
冷样本单列 curl 获取原包的网络 wall time；随后 SDK helper 从已校验缓存离线
物化，热样本不再获取网络。此协议测量固定包的获取，不声称包含实时 registry
catalog 查询或对整个公网的延迟估计。

独立保护上限：compile_link/build_pipeline 各 600000 ms，run 120000 ms，
network_fetch/其他受控命令 180000 ms，另有 CI job 60 分钟上限。这些不是 v1 默认值。
任何命令触及保护上限记 censored，duration_ms=null，仅保留 observed_wall_ms；
不得参与正常完成样本统计。测量器不会修改原 SDK/依赖以让任务通过。测量完成
与功能期待满足分开；常规编译失败真实计时保留，运行未开始则保持固定空状态。

默认值推导规则在正式采样前固定：compile 使用最大可用 compile_link 样本 ×4
加 5000 ms，至少 30000 ms，再向上按 1000 ms 舍入；run 使用最大可用 run 样本
×4 加 1000 ms，至少 5000 ms，同样舍入。×4 与加性部分是明确的波动/启动裕量，
不是从 5 个样本估计的分位数；保守下限避免用微型项目推出脆弱的亚秒默认值。
网络、依赖准备、复合 CLI probe 都不纳入这两个值。正常功能失败保留在汇总中；
被信号异常结束的阶段不作为默认值推导样本。原始阶段和失败日志不能删除。

实现前交付的基线记录必须关闭 B01/B02，并给出宿主 OS/架构、核心数、SDK 包
摘要、编译器/runtime 身份、参数、环境条件、冷热定义和每项原始结果。

## E0 外部使用验证

开始比较前固定一组已有真实项目及版本、任务输入、依赖/lock、可检查输出与
交付方式；至少包含一个有发布依赖的应用和一个有本地依赖/资源文件的项目。
用干净宿主或隔离目录安装实际 SDK；编译器源码目录不可见，未声明环境覆盖为空。

每个任务分别由用户流程与 AI 流程执行同一 create/add/check/test/run/交付步骤。
记录每步命令、退出码、报告、耗时、修复轮次、人工介入原因、完成/未完成与
工具/用户/依赖/未知分类。维护者替换命令、补路径、手改缓存也算介入，不能抹去。
从同一快照重复冷/热路径；失败样本保留，不能临时改任务来改善完成率。

0.11 对照和 0.12 候选的结果分别记录；候选比对不能借旧包的通过回执充当新包
验收。任务脚本/固定身份形成 E0 准入材料，不在本设计包中虚报实际项目成功。

## 候选冻结与发布条件

1. B0、PL、I1–I3、E0 的相应用例与真实记录完成；没有开放的命令契约关键问题。
2. 冻结候选 SHA、版本、SDK 身份、policy 与包含平台范围；所有正式目标取得完整
   同 SHA 资格和实际包重放，缺失/失败/dirty/身份冲突均阻断。
3. 冻结 source run/attempt、原始归档、摘要及回执；Intel 可不包含，但状态必须
   如实记录。包含 Intel 则 basic 身份、原始字节与运行回执必须通过。
4. 经审核的已验证产物入口创建 annotated 标签和未公开 draft，原始字节直接复用，
   不因标签或控制工作流维护重建包。回读 draft 逐包核验；失败停止。
5. 公开发布与 Latest 选择仍是单独授权阶段，经版本政策匹配的推广验证器和
   release-publication 流程检查后执行。默认不能把“已有 draft”当作已发布。
6. 标签、资格、包和公开状态形成不可变发布记录；发布后的支持政策改变不能
   回写历史资格。Edition 正式冻结由独立兼容性证据决定。
